# Decisions Appendix — every micro-fork, pre-decided

Companion to `SPEC-V2.md` (which holds D-1/D-2/D-3, the deliberate deviations). Decisions here are numbered E-### and are **not open for builder interpretation**. "Grounded" notes cite the Hermes code verified 2026-11-03; where a decision contradicts what the code does today, the phase todo says so explicitly.

## Storage & naming

- **E-001 Home database.** All new tables go in the kanban database (the file `kanban_db_connect` resolves per board). No new tables in `state.db`, no new database files. *Grounded: delivery_ledger.py runs its own SQLite file today — that is the anti-pattern this decision exists to prevent repeating.*
- **E-002 Table names.** `sa_triggers`, `sa_decisions`, `sa_mandates`, `sa_inputs`, `sa_subscriptions`, `sa_outbox`, `sa_source_cursors`, `sa_meta`. Tickets = existing `tasks` table; Assignments = existing `task_runs` table. The `sa_` prefix marks Super-agent tables so a reader never confuses them with kanban's own. Do not create `sa_tickets` or `sa_assignments`.
- **E-003 Mandate link.** `tasks` gains two nullable columns: `mandate_id INTEGER` (FK to `sa_mandates.id`) and `ticket_kind TEXT` (`coding|personal`, NULL = legacy kanban task, not a Ticket). Added via the existing column-migration mechanism in `kanban_db_connect.py` (the nullable/defaulted-columns list), never by editing the v1 CREATE TABLE.
- **E-004 Do NOT reuse `kanban_notify_subs`.** That table is task→human notification (gateway tails `task_events`, pings the requester). `sa_subscriptions` is the reverse direction (thread→task). Different direction, different table. Reusing it is a defect.
- **E-005 ID formats.** Triggers: `trg_<uuid4hex12>`. Decisions/Mandates/Outbox rows: SQLite autoincrement integers. Tickets keep kanban task ids unchanged. Threads: `<source>:<source-scoped thread key>` (e.g. `github:pr-123-comments`, `telegram:-100123:456`). The thread key is defined by the Source, per v2 spec.
- **E-006 Timestamps.** INTEGER epoch seconds, matching kanban (`created_at INTEGER`). Never ISO strings in new tables.
- **E-007 Idempotency.** `sa_triggers.idempotency_key` = `<source>:<source-scoped event id>`, UNIQUE index. A duplicate insert is a silent no-op returning the existing row id (INSERT OR IGNORE + select). This mirrors `tasks.idempotency_key` semantics. Never raise on a duplicate.
- **E-008 JSON columns.** Suffix `_json`, stored as TEXT via `json.dumps(..., sort_keys=True)`. No JSON1 queries in v1; read-and-parse in Python.

## The Orchestrator (single writer)

- **E-009 Module.** New module `hermes_cli/orchestrator.py` (plus split siblings only past ~800 lines, named `orchestrator_<part>.py` following the repo's split-file convention). It is the only module that INSERT/UPDATEs the `sa_*` tables and the two new `tasks` columns. All other code calls its functions or reads via `orchestrator_reads.py` query helpers.
- **E-010 Transactions.** Every Orchestrator command that changes a Ticket and queues an Outbox message does both in ONE sqlite transaction on the kanban connection (the store-then-do rule). Use the existing connection/transaction helpers in `kanban_db_connect.py`; do not open a second connection to the same file inside a command.
- **E-011 Threading.** The Orchestrator is called from the gateway process (async) and the dispatcher tick (sync). All public functions are synchronous and use the kanban layer's existing locking; async callers wrap with the repo's existing sync-in-executor helper if one is used by neighboring gateway code — match `gateway/kanban_watchers_dispatcher.py`'s existing pattern exactly, do not invent a new one.

## Gate & Eval

- **E-012 Gate location.** New module `hermes_cli/superagent_gate.py`, pure functions, no I/O except reading the Policy snapshot passed in. Input: trigger dict + policy dict. Output: `(strength, basis_dict)` where strength ∈ `explicit|inferred|not_admitted`. Unit-testable without a DB.
- **E-013 Policy snapshot.** A plain dict built by `orchestrator.policy_snapshot()` from the `superagent` config block + per-Source parts; `policy_version` = first 12 hex chars of sha256 of the canonical JSON (`json.dumps(policy, sort_keys=True)`). The version is recomputed on every snapshot build; snapshots are built per Eval batch, never cached across batches.
- **E-014 Admission defaults.** Exactly the v2 spec table: listed+addressing = explicit; listed+not addressing = inferred; unlisted+addressing = ignore; unlisted+not addressing = ignore; listed bot = inferred (bot list only); cron/first-party = explicit (basis `via=first_party`). No other defaults exist.
- **E-015 Eval call.** Use `call_llm` / `async_call_llm` from `agent/auxiliary_client.py` with task name `superagent_eval` (config: `auxiliary.superagent_eval.provider/model`). *Grounded: call_llm is the centralized aux API and resolves `auxiliary.<task>.*` config.* Never call a provider SDK directly. Eval timeout: 60 seconds, from config `superagent.eval_timeout_seconds` (default 60). Timeout → Decision `unavailable` path after requeue rules (E-017).
- **E-016 Eval prompt & output.** The prompt template lives at `prompts/superagent/admission.md` inside the repo's existing prompt-asset location used by neighboring features — if none exists, `hermes_cli/superagent_prompts.py` as a module constant; builder: check for a prompts directory convention first, use it, else the module constant. Output: the model must return JSON `{"judgements": [{"rule": "<name>", "match": true|false, "evidence": "<one line>"}], "intent": true|false}`. Unparseable output = assessment failure = Decision `unavailable` (never a silent ignore).
- **E-017 Eval batching numbers.** Per-Thread lock: one running Eval per Thread, enforced by a `sa_threads`-free design — the lock is a column, not a table: `sa_triggers.eval_state` ∈ `queued|evaluating|done` plus `thread_key`; a batch = all `queued` triggers for one thread_key, capped at **20** (excess waits for the next batch). Requeue on expiry: max **2** requeues, third = `unavailable`. Batch assembly runs in the dispatcher tick (Phase 2), not on inbound.
- **E-018 Router batching.** The Router decides up to **10** candidates per `orchestrator_route` call (matches dsh's batch-decision shape). Items are processed independently; a refused item never blocks others.

## Router & Workers

- **E-019 Router tool names.** New tools registered for the Router profile only: `orchestrator_route`, `orchestrator_eval`, `orchestrator_eval_read`, `orchestrator_eval_decide`, `orchestrator_reply`, `orchestrator_read`, `orchestrator_ticket_retry`, `orchestrator_ticket_request_status`, `orchestrator_ticket_note`, `orchestrator_trigger_requeue`, `orchestrator_thread_unsubscribe`. Implement in `tools/orchestrator_tools.py`, schemas in `tools/orchestrator_tools_schemas.py` (mirrors the kanban tools split). Reuse existing tools where they already do the job: status reads use `kanban_show`/`kanban_list`; do not duplicate them.
- **E-020 Worker silence.** Worker runs must not receive: `clarify`, `send_message`, `memory` (writes), `cronjob_manage`, and any present/UI tool registered in the profile. *Grounded: `DELEGATE_BLOCKED_TOOLS` in `tools/delegate_tool_toolsets.py` already blocks exactly clarify/send_message/memory/cronjob_manage/delegate_task for delegate children.* Implementation: for kanban-dispatched workers, extend the dispatcher's worker toolset resolution to apply the same blocked set (plus present/UI); do not create a second blocklist — import and extend the constant. Orchestrator-role children keep `delegate_task` per existing role rules.
- **E-021 Worker report path.** Workers report ONLY through existing kanban tools: `kanban_heartbeat`, `kanban_block` (with typed `block_kind`), `kanban_complete`, `kanban_request_review`, `kanban_request_changes`, `kanban_comment`. The Report vocabulary maps: progress→heartbeat/comment; waiting→run end with no block; ready→`kanban_request_review` or complete; blocked/failed→`kanban_block`; dropped→complete with outcome marker in summary prefix `DROPPED:`. One Attention question = the body of a `kanban_block` with `block_kind=question` if that kind exists in `VALID_BLOCK_KINDS`, else a `task_comments` row authored `worker:attention` — builder: check `VALID_BLOCK_KINDS` first, use the first that applies, record which in REPORT.md. No new report tools in v1.
- **E-022 Shell auto-background.** Scope: kanban-dispatched worker runs only. Mechanism: pass the existing terminal tool's background configuration for the run so foreground commands background after **5 s**; if the terminal tool has no such threshold setting, that todo is a blocker (do not modify the terminal tool's global defaults). Record the finding in REPORT.md either way.
- **E-023 Slots.** Slot state is in-memory in the dispatcher process (a counting structure in `kanban_watchers_dispatcher`), NOT a table — slots are a runtime fact, and a restart correctly frees all slots (Assignments are recovered from `task_runs`, not from slot state). Human reserve = 1 slot, usable only by a wake whose newest Input `is_person=1`; wakes take priority over launches in the tick's ordering (existing tasks-waiting-for-person before new ready tasks — match dispatcher's existing priority order where it exists).
- **E-024 Models.** Config keys: `superagent.router_model`, `superagent.eval_model`, `superagent.worker_model`, each `{provider, model}` or null. Worker model applies through the EXISTING per-task columns `tasks.model_override` / `provider_override` at dispatch. Router model = the gateway profile's model setting when the router profile is active. Eval model = `auxiliary.superagent_eval.*` (E-015). No new model-resolution code.

## Sources, Subscriptions, Outbox

- **E-025 GitHub Source polling.** Poll, don't webhook (Hermes has no inbound HTTP listener for this in v1 scope — the VM/gateway accepts no inbound connections). Interval **60 s**, aligned to the dispatcher tick; cursor (last-seen notification id / timestamp per scope) stored in a new `sa_source_cursors` table (`source`, `scope`, `cursor`, `updated_at`). Reads via the agent account's `gh` CLI through the existing command-running utilities; repo scope = exactly one repo from config `superagent.github.repository`. GitHub Enterprise: refused at config validation with a clear error.
- **E-026 Trigger fan-out.** On Trigger insert, the Orchestrator checks `sa_subscriptions` for the trigger's thread_key (and correlated thread keys listed in the trigger's `correlation_json`): owning subscriptions get an Input row; context-only get an Input row flagged `context_only=1`. Inputs are rows in a new `sa_inputs` table (`ticket_id`, `trigger_id NULL`, `kind` ∈ `trigger|policy_change|note|resume`, `body`, `is_person`, `read_at NULL`, `created_at`). A person's Input delivered to an ended, unstopped Ticket triggers revalidation then resume (v2 §2.5) — implemented in Phase 3, not before.
- **E-027 Handback.** `orchestrator_trigger_handback` equivalent for workers is a kanban tool addition ONLY if E-021's set cannot express it — it cannot, so: add ONE tool `kanban_handback` in `tools/kanban_tools.py` (+ schema) with args `(trigger_id, reason)`. A Ticket hands back a given Trigger at most once; second call returns an error string, never raises.
- **E-028 Outbox send path.** Outbox rows: (`id`, `ticket_id NULL`, `channel` (source), `address_json` (platform/chat/thread), `purpose` ∈ `acknowledgement|answer|result|attention|notice`, `body`, `status` ∈ `queued|sending|sent|failed|dropped`, `attempts`, `next_attempt_at`, `receipt_json`, `created_at`, `sent_at`). Sender: a dispatcher-tick-driven drain calling the gateway's EXISTING platform send path (the same function platform adapters use for proactive sends — builder: locate it in `gateway/platforms/base.py` / `gateway/delivery.py` neighbors; use it, don't write a new sender). Retry backoff: 5 s doubling to 300 s, `attempts` increments per try; after 3 consecutive failures the row is a panel-visible problem but keeps retrying until dropped-by-source-verdict (E-029).
- **E-029 Dropped messages.** Drop only on the Source's verdict that the conversation is gone/unreachable (platform error codes mapped per platform in the drain function, conservative: unknown errors are `failed`, never `dropped`). Dropped rows keep `dropped_reason` and are never requeued.
- **E-030 100-word cap.** Enforced in the Outbox drain for channels whose Source declares `im_cap=true` (chat platforms; NOT GitHub, NOT mail): body word count > 100 → the row fails with error `over_limit` and a notice Trigger goes to the Router. Never truncate silently.
- **E-031 Migration of existing delivery.** Phase 4 migrates: (a) kanban notifier sends (`kanban_db_notify` path), (b) cron delivery for agent-originated messages. It does NOT migrate: async-delegation completion events (different direction), pairing/decline notices, or the delivery_ledger's flood-control helpers (`flood_wait_seconds` etc. in `gateway/delivery_ledger.py` — the drain must CALL these for rate-limit backoff; they are a library, not a queue). The ledger's queue rows, if any remain after migration, are left readable, not deleted.

## Panel & config

- **E-032 Panel home.** Extend the existing kanban dashboard surface (the one serving boards/tasks) with a Super-agent view; do not build a new app. Stage computation is a pure function `orchestrator_reads.ticket_stage(ticket_row, latest_run, open_attention, delivery_state)` implementing the v2 first-match table; the panel and the Router's `orchestrator_read` both call it. Stage is never stored (v2 rule).
- **E-033 Config block shape.** Exactly:

  enabled: false            # master switch; false = today's Hermes, untouched
  accept_mode: observe      # off | observe | auto
  eval_timeout_seconds: 60
  worker_slots: 4
  human_reserve_slots: 1
  router_model: null        # {provider, model} or null = profile default

- **E-034 Tests.** pytest, `tests/` tree (pyproject `testpaths=["tests"]`). New tests under `tests/superagent/` mirroring module names (`test_gate.py`, `test_orchestrator.py`, …). Use the existing kanban test fixtures/temp-DB pattern — builder: find how existing kanban tests create temp DBs and copy that pattern exactly. Acceptance command per phase is in its TODOS.md.
- **E-035 Branch & worktree.** All work on branch `superagent-p<n>` in a worktree of the Mac Studio checkout; the live checkout's running processes are never restarted by the builder (contract rule 11). Merges happen only at reviewer sign-off.

## Execution (Hermes-native mode — added 2026-11-03, see HERMES-BONSAI-RUNBOOK.md)

- **E-036 Cards are the live state.** The supervisor imports the pack into a `superagent-build` board before any building: parent card per phase, child card per todo, `task_links` for parentage and dependencies exactly as the TODOS dependency lines state. In Hermes mode the cards are the tracker; the markdown pack is the archive, written only by the supervisor.
- **E-037 Context packets.** A builder receives only its card's packet (todo verbatim, named files + anchors, excerpted decisions, acceptance command, 5-line stop protocol). It never receives SPEC-V2 or full DECISIONS.md. Packet gaps are supervisor defects, fixed by packet amendment.
- **E-038 Bonsai serving.** Bonsai 2 27B runs on the Mac Studio via the **MTPLX app** (primary route — Adam, 2026-11-03: Bonsai is available in MTPLX and loadable into any OSS harness on the system), registered as a custom provider in the worker profile only, bound to local access. - **E-039 Smoke gate.** No Bonsai card runs before the `SMOKE-bonsai` card passes: 20 scripted micro-tasks, ≥19 correct, zero invented tools, zero out-of-scope touches. The gate tests tool-calling — the measured weak point — not reasoning.
- **E-040 Builder tiers (per card, set via `model_override`/`reasoning_effort`).**

- **E-042 Review binds the sha.** Every card pass and phase sign-off records the commit sha reviewed; a changed diff voids the pass. Reviews read the diff, the acceptance output, and `task_events` — never the worker's summary prose alone.

## E-044 — sa_mandates.ticket_id is NOT unique (D-1 amendment chains) — supervisor amendment, 2026-11-03
The Phase-2 DDL as originally packed declared `sa_mandates.ticket_id TEXT NOT NULL UNIQUE`, which makes D-1's amendment chain (a new mandate row with `amended_from` set, the old row marked `superseded`) impossible — card 2.6's builder proved the contradiction empirically and stopped per protocol. Resolution: `ticket_id` carries NO unique constraint; an index `idx_sa_mandates_ticket` on (ticket_id) replaces it. The invariant "exactly one status='active' mandate per ticket" is enforced at the application layer by accept/amend_mandate, not by the schema. Migration note for cutover: DBs whose sa_mandates table was already created WITH the unique constraint need a table rebuild (CREATE-copy-drop-rename); all build-phase DBs are temp/test, and no production DB has sa_mandates rows while superagent.enabled is false — the rebuild procedure is a cutover checklist item, not a build blocker.
